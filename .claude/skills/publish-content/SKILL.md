# 發布本站內容

這個 skill 是**流程與驗收清單**。規則本身以 `CLAUDE.md` 為準（發布流程、寫作規則、敏感資訊處理、上鎖），格式細節見 `README.md`；兩邊有出入時以 `CLAUDE.md` 為準，並告訴編輯哪裡不一致。

開始前先判斷是哪一種：

| 類型 | 素材 | 合併前要編輯確認嗎 |
| --- | --- | --- |
| 導讀文章 `/articles/` | 原文網址 | 不用（先發布、後審查） |
| 實作單元 `/notes/`、`/packages/` | `inbox/<資料夾>/` | **要**：先傳預覽給編輯，編輯確認後才合併 |

第一次回應依編輯的溝通偏好：一句話確認理解；有需要編輯決定的事（系列命名、章節放法、要不要改舊章節）給 2–3 個選項附優缺點，等編輯選完再動手。單純照流程走的部分不用問。

## 寫作的通用原則

這些是過去編輯修正過的地方，每篇都要套用：

1. **查證過就用肯定語氣。** 從官方來源（CVE API、USN、官方文件、套件資訊）查到的事實直接寫，不加「應該」「推測」「可能」這類推論字眼。查不到的才用 `> **待確認**：…`。不要把查得到的事寫成推論，也不要把推論寫成事實。
2. **編輯直接說明的事實就是事實。** 編輯在對話中說明了自己的環境或操作（例如預設版本、自己手動升級過什麼），就照實寫進文章，並移除對應的待確認。
3. **模擬結果和實際狀態分開寫。** `--dry-run`、`--simulate` 這類輸出是「如果執行會怎樣」，文章要寫清楚：模擬顯示的結果是什麼、實際上有沒有變更、系統目前的實際狀態（例如版號沒變、漏洞仍在）。
4. **編輯的口語說法要改得更精確時，回報裡要說明。** 意思不變但改了措辭（例如把「已經解決了」改成「模擬結果顯示可修補，但實際沒有更新」），在對話中列出改了什麼、為什麼。
5. **編輯沒實測、但屬於最佳實踐的步驟**，標「本站補充，未實測」，寫出依據（官方文件或套件行為），並給讀者驗證的方法。不要寫成編輯做過。
6. **版號、pocket、套件元件（main／universe）以官方資料為準。** 安全相關優先查 `https://ubuntu.com/security/cves/<CVE>.json`；網路擋住的來源（例如 Launchpad）不要靠記憶補，改查其他官方來源或標待確認。
7. **系列文章**：新增一章時，「系列小結」移到最新一章；上一章的小結改成「這一章的小結」並指向下一章。`series.yaml` 的標題與簡介要涵蓋所有章節。舊章節除了這些銜接處，不主動改寫，除非編輯要求。
8. **技術內容寫給學習者看**：技術名詞保留英文並附繁體中文說明；語氣中立，用學習者的角度，不寫成專家建議。

## 流程 A：導讀文章

1. 讀原文（`WebFetch` 或 web-fetch agent）。只根據原文與可查證來源撰寫。
2. 新增 `src/content/articles/<slug>.md`：frontmatter 欄位見 `README.md`「文章格式」；`pubDate` 用今天；必要區塊 `## ikusupuroa 觀點`、`## 原文精華導讀`（結尾附 `### 出處`）。標籤沿用既有分類。
3. `src/data/sources-state.json` 記錄為 `published`（`article` 填 slug、`processedDate` 填今天）。
4. 跑下方「驗收清單」。
5. 開 PR → 等 `build` 檢查通過 → 直接合併 → 確認部署成功。
6. 回報：網址 `https://ikusupuroa.github.io/ClaudeCodeOnTheWeb/articles/<slug>/`、觀點重點、所有「待確認」與「本站補充」段落。
7. 若來自 `new-articles` Issue：略過的篇目標 `skipped` 加 `note`；整個 Issue 都處理完後留言說明結果並關閉 Issue。

修改：改完同樣直接合併並回報。下架：照 `CLAUDE.md` 加 `draft: true`、狀態改 `unpublished` 加 `note`。

## 流程 B：實作單元（技術筆記／套件功能）

1. **讀完 inbox 所有素材**（說明、指南、操作紀錄、截圖都要看）。不自行編造操作結果或畫面。
2. **敏感資訊**：依 `CLAUDE.md`「敏感資訊處理」把文字和檔案換成假資訊；每張截圖都要看過，有敏感資訊就告訴編輯是哪一張、哪個位置，處理好之前不放上網站。
3. **決定放法**：單篇或系列第幾章；有截圖用資料夾＋`images/`。必要區塊：技術筆記 `## 探討議題`、`## 實作筆記與畫面`；套件功能 `## 產品介紹`、`## 技術文件導讀與實作`（`references` 至少一份官方文件、要填 `product`）；系列第 2 章起第一個區塊改成 `## 前情提要`。
4. **撰稿**：
   - 要讀者執行的指令用 ` ```bash `，不含提示字元；輸出用 ` ```text `；一個區塊不混放指令和輸出。
   - frontmatter 的 `environment` 寫清楚實作環境與版本（用假的主機名稱）。
   - 套用上方「寫作的通用原則」。素材沒交代清楚的步驟標「待確認」，並在回報中詢問編輯。
5. 截圖從 `inbox/` 搬到文章資料夾，處理完的 inbox 素材在同一個 PR 刪除。
6. 跑下方「驗收清單」。
7. 開 **draft PR**，用 Playwright 截圖（桌面與手機）傳給編輯預覽，同時**問編輯：這篇（或這一章）要不要上鎖？**
8. 編輯確認後才合併（編輯明確說「直接合併」時例外）→ 確認部署成功 → 回報網址、待確認與本站補充段落、敏感資訊替換清單。

## 驗收清單（兩種都要跑）

詳細指令見 `checks.md`。

- [ ] `npm run build` 零錯誤、零警告
- [ ] 敏感資訊掃描：沒有真實的使用者名稱、主機名稱、本機路徑、IP、MAC、Email、Token；IP 只出現 `192.0.2.x`／`2001:db8::x`
- [ ] 程式碼區塊：`bash` 只放指令、輸出都是 `text`
- [ ] 手機版（寬 390px）頁面沒有橫向跑版；常見原因是很長的行內程式碼或網址，改寫句子或拆開
- [ ] 所有「待確認」「本站補充」都列進回報
- [ ] 查證過的事實沒有推論字眼；模擬結果沒有被寫成已完成

## 合併與部署

1. 在指定的開發分支 commit（訊息結尾加 attribution），`git push -u origin <分支>`，開 draft PR 並訂閱 PR 活動。
2. 等 `build` 檢查通過；需要編輯確認的，等編輯確認。
3. PR 轉成 ready → 用完整 head SHA 合併。
4. 合併後把開發分支重設到最新 `main`（`git fetch origin main && git checkout -B <分支> origin/main`，再 force-with-lease push），下一篇從乾淨的基礎開始。
5. 用 `actions_list`（`deploy.yml`、`main`）確認部署 `conclusion: success`，再回報。環境的網路通常連不到 github.io，不要用 curl 檢查網站。

PR 說明、commit 訊息只寫敏感資訊替換的**類型與數量**，不寫真實值。
